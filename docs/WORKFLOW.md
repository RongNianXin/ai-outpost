## 日常开发规则

- 简单任务直接轻量执行。
- 复杂任务先说明执行方式，再进入设计、调试或验证流程。
- 只读取完成当前任务真正需要的文件。
- 修改范围保持最小，不提前实现 V2/V3。
- 当前优先级高于社媒平台接入：稳定官网周更、自动校验、确认上线。
- 完成后更新 `progress.md`。
- 如果发现长期有价值的约束、坑点或判断，更新 `findings.md`。
- 如果阶段状态、下一步或验收标准变化，更新 `task_plan.md`。

## 优化建议的状态与落盘

每个会改变长期流程的建议都标记为以下一种状态，不能只留在聊天中：

- `讨论中`：只有想法或证据不足；写入findings或task_plan待办，不改变现行做法。
- `已采用`：用户明确认可，或AI对低风险流程建议完成对抗式审查后按授权实施；合并到唯一归属的现行规则，并在progress记录依据、改动和验证。
- `暂缓/否决`：保存原因、适用条件和重新评估触发点，防止继任者重复采用旧方案。
- `已替代`：现行规则直接更新，历史记录注明替代关系，不同时保留两套互相冲突的指令。

采用前检查目标误解、证据强弱、边界和副作用。涉及费用、权限、外部写入、不可逆动作或显著产品方向时仍需用户确认；本地低风险流程修订按当次授权执行。讨论结论只有进入对应现行文档并在task_plan/findings/progress留下状态后，才算可交接成果。

## 复杂任务规则

以下情况需要更重流程：

- 新子系统。
- 跨多个模块。
- 影响内容 schema、发布闸门、构建流程或部署流程。
- 涉及安全、成本、自动化发布、数据迁移或用户数据。
- 涉及周更运行状态、通知确认、中断发布或平台分发。
- 修复难以定位的 Bug。
- 最终发布前验收。

重流程要求：

1. 先澄清目标和验收标准。
2. 必要时给 2-3 个方案和推荐方案。
3. 获得确认后再修改。
4. 变更后运行必要验证。
5. 把结果写入 `progress.md`，把长期结论写入 `findings.md`。

## 故障中断后的新消息恢复门禁（2026-09-19，已采用）

这是一条项目级恢复规则，不声称修改 Codex 产品本身的运行机制。只要当前回合在“完成”或“明确暂停”前因模型容量、模型切换、超时、工具失败、进程退出、连接重置、窗口/会话切换等原因结束，后续收到用户消息时，先处理旧任务状态，再决定是否纳入新任务。

1. 在回复或执行新消息前，先只读回读 `task_plan.md`、`progress.md`、`findings.md` 及旧任务引用的现行规则；必要时核对 `git status --short`、当前分支/HEAD、相关进程与端口。不得把上一次未完成的工具调用、权限、远端授权或完成声明当作事实继承。
2. 将旧任务归类为：`completed`（有验收证据）、`blocked`（有明确且仍存在的阻断）、`paused`（用户明确暂停）或 `interrupted`（其余默认情况）。发生容量/故障报错而没有完成证据时，默认是 `interrupted`，不是完成，也不是用户放弃。
3. `interrupted` 默认从最后一个已落盘 checkpoint 的下一步继续；若新消息与旧任务同一目标或同一链路，合并处理。若明显是新目标，先向用户报告“旧任务断点 + 新任务关系 + 最小下一步”，不能仅因用户说“开始新任务”就静默丢弃旧任务。只有用户明确说“放弃/停止旧任务”才关闭旧任务。
4. 旧任务状态未明确前，不执行新消息中的外部写入、发布、部署、远端操作或其他不可逆动作；继续时重新核对本轮授权，不继承旧授权。若没有可用 checkpoint，只能依据实际文件、工具输出和工作区状态回源，明确标出可能缺失的中间成果。
5. 每个长任务在开始、关键里程碑和外部写入前更新 `task_plan.md` 的目标/断点/权限，并在 `progress.md` 记录已做、证据和未做；故障恢复时从这些记录与实际产物重建，不补写虚构结果。
6. 恢复汇报至少包含：旧任务状态、精确 checkpoint、已验证事实、未完成/阻断项、与新消息的关系、下一动作。若当前会话/历史无法恢复，只能报告“会话级恢复不可用”，再依赖项目文件继续；不能声称已实现产品级自动续接。

建议用户在同一任务中发送“继续刚才被中断的任务，先读取并报告断点，再从下一步继续”；若确实要改做新事，明确发送“放弃刚才任务，开始新任务”。

## Git 规则

- 默认不自动提交 Git。
- 默认不推送、不合并、不创建 PR。
- 本地提交或打标签须有明确授权；授权可以包含在首次本地执行包中，无须在修复、验证完成后再问一次。远端写入另按执行前最终确认处理，不能从本地授权推定。
- 执行 Git 前先检查 `git status --short`。
- 提交后报告 commit 和 tag。

## 发布前检查

### 发布阻断复盘：先核对“发布轨道”再准备内容（2026-09-19）

第004期发布前出现的两个阻断不是发布脚本临时失效，而是此前就存在、且按设计生效的保护：

- 工作区从第003期之后持续保留了代码、配置、文档和用户未跟踪资产。官网适配器只允许本期 JSON、来源目录、运行记录、主视觉和本期审查文件进入发布提交；任何代码或配置改动都会停止发布，防止把无关成果一起推送。
- 上一期发布完成后，运行状态按安全规则恢复为 `draft_only`，并仍绑定旧期号。它表示“只准备、不外发”，不是新一期的发布许可；第004期不能继承第003期的状态或授权。

此前“没遇到”主要是因为当时发布范围正好落在允许的内容文件内，且发布前已暂时满足对应期号和分支条件；不能据此假设工作区长期干净或运行状态会自动滚动到下一期。

以后每期在预览通过时先记录两项基线：`git status --short` 的非本期改动清单，以及 `ops/weekly-run-state.json` 的模式和 `issueId`。正式发布前按以下顺序复核：

1. 当前期刊仍是用户确认的具体版本，且 `status=approved`；
2. 工作区只有本期允许路径，或无关改动已由用户明确保存到独立版本；不使用 reset、清理或隐式暂存规避检查；
3. 运行状态由用户明确授权切换到 `normal`，并绑定当前期号；`draft_only`、`paused`、`emergency_stop` 或旧期号一律停止；
4. 再运行内容校验、链接检查、类型检查、lint、测试和构建，最后才执行发布确认句；
5. 发布完成后回读公开页面和下载文件，并按用户要求恢复安全模式，记录恢复后的期号和回执。

这套流程不会自动切换 `normal`，也不会自动保存、提交或删除无关改动；它只把阻断提前暴露，减少临到发布才发现返工。

公开发布前必须确认：

- 本期内容已经完成 AI 交叉核查、离线校验和发布前链接检查。
- `publishedAt` 已填写。
- 期刊状态已切换为 `published`。
- 内容校验、链接检查、公众号导出、类型检查、lint、测试和构建均通过。
- 首页、归档页、关于页和期刊详情页可访问。
- 移动端无横向滚动。
- 项目作者已确认发布；如果周更运行状态是 `paused`、`draft_only` 或 `emergency_stop`，不得发布。

## 周更自动化规则

- 按CONTENT-OPS的“选题漏斗”先发现线索、核验证据、分维度排序，再列本周三件重磅候选；交稿前复查遗漏。官方确认发布事实，独立评测和可信博主补充实际体验，分别归因。热度负责发现，不直接决定入选或头条。

- 官网是主站；本地期刊JSON是共同事实底稿。先集中审查底稿，再派生本轮目标平台、逐项对照并预览，最后分别授权发布；不能把旧线上版本当成本地修订已部署的证据。纠错等级与同步方法统一见PROMOTION“发布后分级纠错与跨平台同步”。
- 每周优先自动完成候选收集、筛选、事实映射、AI 交叉核验、中文草稿和预览。
- 正式期刊title严格为“AI 前哨站第 NNN 期”，主题留摘要/导读，内部slug不随标题改；每期最多一张可选原创无字主视觉，情报卡不机械配图。
- 事实稿完成后先做独立文风改写，再运行 `content:validate` 的模板词检查；自动检查不能冒充 AI 检测器，真实页面人工审核仍是发布门禁。
- 作者审定按PROMOTION“作者立场审定：白话确认与逐句对照”：AI从现稿列具体意见并解释，作者表达认可/反对/不理解，AI核对全文并列必要改句。技术事实由AI查证，不转嫁给作者。已确认立场沿用，只有实质变化才局部重问；不将立场确认混同稿件批准、原创资格或发送许可。
- 上线前保留人工确认关卡；不允许 AI 全自动绕过确认直接发布。
- 内容不足时允许短版或跳过。
- 公众号与小红书均先生成预览和派生稿；公众号完整稿沿用官网视觉，由作者实质编辑与审定，AI辅助核验/审校/排版，作者集中粘贴上传，AI复核平台结果。每期交齐HTML、备用Markdown、独立图片、字段和编号人工步骤；不能把全文缩成小样。第002期手工粘贴预览已由用户确认，后续每期核对完整性与入口；详细步骤及原创/AI规则见 PROMOTION.md，项目长期要求见根目录AGENTS.md。小红书先发私密测试；各平台验证后仍需最终发送授权，不默认浏览器逐段写稿。
- 公众号 AppSecret 和小红书 Cookie 只保存在本机，不进入 GitHub、日志或聊天。
- 三个平台分别保留确认门禁和幂等回执，不提供绕过审核的“一键全发”。

## 交接完整性门禁

来源私密化后，公开记录仅保存脱敏方法与状态；内部依据、候选和研究履历见.local/source-library/research-notes及其引用资料。交接与新会话必须经content:research:start读取私密入口。快照只保留指针、指纹和脱敏断点，不复制私密正文；清单schemaVersion=2包含整个私密目录（排除.git）的聚合指纹，缺少指南、目录或研究入口不能宣布生产交接就绪。目录外引用资料仍独立核验；旧路径说明以本段及来源模块指南为准，不自动修改实际调度。

交接目标是让继任者获得继续判断和执行所需的同等信息，不承诺复现上一任的全部聊天、主观记忆或未记录想法。必须保留目标、事实、证据、已采用/暂缓决定、当前文件版本、未完成项、验证结果、权限和禁止项。

旧总指挥按以下顺序收口：

1. 处理本阶段有实质影响的建议状态，将已采用规则合并到唯一归属文档；更新task_plan当前断点、findings依据和progress执行记录。
2. 回读AGENTS、task_plan、findings、progress及本任务引用的现行文档，核对冲突、待确认项、未提交文件、当前Git HEAD、运行状态和外部权限。运行 `pnpm.cmd content:research:start` 与 `pnpm.cmd ops:check`；它们只验证本地来源入口和周状态，不自动生产或发布。
3. 最后按handoff技能生成Temp目录中的交接快照。快照引用现有资料，不复制成第二套规则；明确事实截点、当前总指挥、未提交清单、候选/阻塞、授权和禁止项，并包含建议继任者使用的skills。删除或概括凭据、个人身份信息及无需交接的私密内容。
4. 运行 `pnpm.cmd ops:handoff:manifest`，把唯一一行 `HANDOFF_CONTEXT {...}` 原样写入快照末尾；再运行 `pnpm.cmd ops:handoff:check -- --snapshot <快照绝对路径>`。清单覆盖权威文档、校验脚本自身、Git HEAD、所有非忽略未提交文件的路径与内容指纹、来源库、本机状态索引，以及现有周六自动任务的状态、周期、是否绑定任务和配置指纹；不写入配置正文或任务ID。失败表示快照缺资料或生成后发生漂移，必须更新受影响记录并重新生成，不能宣布交接就绪。

文件指纹只能检测变化，不能判断讨论是否漏记。收口时另核对本阶段用户决定、反对理由、未采纳方案、待确认事实和下一步是否均有资料出处；继任者必须据这些出处复述当前决策、未完成项与权限，无法回答处标为缺口并回源。被Git忽略的必要工具、导出稿和外部规则按现有指针另行核验可读性与版本；清单不打包文件，也不保证换机器后本机资料仍在。当前周六任务直接必读CONTENT-OPS，WORKFLOW由AGENTS及本节提供规则入口；不能把提示词要求读取等同于未来每次运行已经执行。

继任者先读快照、AGENTS、task_plan、findings和progress，再读快照及当前任务引用的规则；随后用同一检查命令复核。检查通过只证明文件版本、来源库、本机索引、自动任务配置指纹、Git HEAD和未提交清单一致，不证明外部网页、平台状态或事实仍未变化。若检查失败、身份不明或快照后有改动，只暂停受影响动作并回源；不继承旧发布、提交、推送、部署或平台写入授权。
