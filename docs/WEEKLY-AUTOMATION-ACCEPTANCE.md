# 周更自动化验收清单

## 目的

本文件用于验收 AI Outpost 的周更自动化能力，不用于审核第 002 期文案。

当前项目的主要目标是：自动检索、自动整理、自动生成、自动验证、提醒人工确认，并在人工确认后尽量一键发布到官网和后续平台。

## 当前真实状态

### 已完成

- 官网内容引擎：使用 `content/issues/*.json` 作为唯一内容源。
- 内容结构校验：`pnpm.cmd content:validate`。
- 来源链接检查：`pnpm.cmd content:check:links`。
- 微信公众号 Markdown 导出：`pnpm.cmd content:export:wechat`。
- 基础工程检查：`pnpm.cmd typecheck`、`pnpm.cmd lint`、`pnpm.cmd test`、`pnpm.cmd build`。
- 周更状态文件：`ops/weekly-run-state.json`。
- 单次运行日志：`ops/runs/2026-W25.json`。
- 官网本地预览：`approved` 状态内容可在本地开发环境查看。
- 生产安全闸门：生产构建只公开 `published` 或 `corrected` 内容。
- 轻量分享包：已能生成面向微信、小红书、X/Twitter 的文案草稿。

### 未完成

- 自动定时检索：目前仍由 AI 在会话中执行，不是独立脚本。
- 自动定时提醒：Codex 2 分钟提醒测试未成功触发，不可作为正式提醒方案。
- 微信提醒：未接入。第一阶段路线改为第三方微信推送服务，Server酱 / WxPusher / PushDeer 三选一，具体服务、额度、费用、稳定性和接口待确认。
- 一键确认：未实现。当前仍依赖用户在对话中明确回复。
- 一键发布官网：未实现。当前仍需人工或 AI 修改状态、提交 Git、触发 GitHub Pages。
- 微信公众号自动发布：未实现，需单独讨论公众号账号、草稿箱、图文格式、API 权限和合规。
- 小红书发布：未实现，需单独讨论内容合集、图文卡片和作品集分类。
- X/Twitter 发布：未实现，需单独讨论账号注册、发布流程和 API 条件。
- 中英文切换：未实现，列入后续版本。

## 验收分层

### 人工验证

人工验证目标是确认“用户能否看懂、能否决定、能否安全放行”。

检查项：

- 能打开本地预览页。
- 能看到本期标题、核心变化、风险提示和来源链接。
- 能看懂运行摘要，不需要阅读英文原文。
- 能明确选择：发布、仅保留草稿、修改后再看、跳过本期。
- 发布前不会自动上线。

本轮人工验证入口：

- 第 002 期本地预览：`http://127.0.0.1:3100/issues/2026-06-18-agent-discovery-cloud-agents-tts/`
- 公众号草稿：`exports/wechat/2026-06-18-agent-discovery-cloud-agents-tts.md`
- 分享包草稿：`exports/social/2026-06-18-agent-discovery-cloud-agents-tts.md`
- 运行日志：`ops/runs/2026-W25.json`

### AI 自我验证

AI 自我验证目标是确认“内容、代码和构建没有明显错误”。

必须运行：

```powershell
pnpm.cmd content:validate
pnpm.cmd content:check:links
pnpm.cmd content:export:wechat
pnpm.cmd typecheck
pnpm.cmd lint
pnpm.cmd test
pnpm.cmd build
```

通过标准：

- 内容 JSON 能通过 schema 校验。
- 所有事实引用都能指向已有来源。
- 来源 URL 在官方白名单内。
- 明确 404 或 5xx 链接不得发布。
- 403、超时、网络中止可记录为警告，但必须写入运行日志。
- TypeScript、Lint、测试和构建必须通过。
- 生产构建不能误公开 `approved` 草稿。

### 交叉 AI 验证

交叉验证目标是让另一个 AI 从审查角度找问题，不让同一个 AI 自问自答。

交叉验证材料：

- `content/issues/issue-002.json`
- `ops/runs/2026-W25.json`
- `findings.md`
- 官方来源链接

交叉验证提示词：

```text
你是一名 AI 内容事实核查员和自动化流程审查员。请审查以下 AI Outpost 周更材料：

1. 检查每条中文事实是否能被给定官方来源支持。
2. 标出任何夸大、推断过度、来源不清、日期冲突或平台能力误写。
3. 检查运行日志是否完整记录候选、淘汰原因、警告和人工确认状态。
4. 判断是否存在未经人工确认就可能上线的风险。
5. 输出：通过 / 需要修改 / 不建议发布，并列出具体原因。

注意：不要补写新内容，不要替作者发布，只做审查。
```

## 最终基建路线

已确定放弃：

- 本地计划任务：用户电脑不能保证 24 小时开机。
- 邮件提醒：用户不常看邮箱，不能作为主要提醒通道。

已确定采用：

- GitHub Actions 定时任务作为 24 小时云端运行内核。
- 第三方微信推送服务作为第一阶段提醒通道，候选为 Server酱、WxPusher、PushDeer。
- GitHub Actions 脚本在周更流程完成后，把草稿结果、校验摘要和确认入口推送到用户微信。
- 第一阶段不做自动发布到公众号、小红书或 X/Twitter，只生成文案草稿，由人工复制发布。

安全边界：

- GitHub Actions 可以自动生成草稿和校验报告。
- GitHub Actions 不应在无人确认时直接公开发布。
- 微信推送只负责通知和承载确认入口，不承担事实审核。
- 第三方推送 token 必须放在 GitHub Secrets，不写入仓库。

目标时间：

本周六目标调整为：

6. 用户确认无误后，手动触发官网发布。

现实拆分：

- 官网自动草稿和校验是本周六核心目标。
- 微信推送可达性是本周六核心验收点。
- 官网发布仍采用人工确认后手动触发，不做无人值守发布。
- 公众号、小红书、X/Twitter 保持第一阶段策略：只生成文案草稿，由人工复制发布。
- 公众号自动发布、草稿箱 API 和图文排版自动化单独讨论，不纳入本周六硬目标。

## 微信推送服务对比

本表只用于第一阶段选型。服务额度、价格、接口稳定性和账号条件都属于易变化信息，实施前必须以官方页面为准。

| 服务 | 初步判断 | 优点 | 风险 / 待确认 |
| --- | --- | --- | --- |
| Server酱 / Server酱³ | 推荐优先测试 | 官方定位是极简推送服务，一个请求即可把消息推到微信等通道；最适合先验证 GitHub Actions 到微信的链路。 | 具体套餐、额度、费用、通道支持和接口格式待确认；需要用户注册并提供 sendkey。 |
| WxPusher | 第二候选 | 有独立开发文档，面向消息推送 API；适合后续更正式的订阅/用户管理。 | 接入步骤可能比 Server酱多，需要应用、用户订阅、appToken / uid 等配置，额度和限制待确认。 |
| PushDeer | 暂不推荐作为第一阶段 | 支持通过 `pushkey` 和 API URL 推送文本/Markdown，文档示例清楚。 | 官方 GitHub 仓库提示项目已不维护，并建议改用持续维护的 Server酱³；因此不适合作为最小稳定提醒链路首选。 |

初选结论：

- 第一选择：Server酱 / Server酱³。
- 备选：WxPusher。
- 暂缓：PushDeer。

第一阶段只验证一件事：GitHub Actions 是否能把“周更草稿已生成 + 校验状态 + 手动发布入口”推送到用户微信。

### GitHub Secret 配置

Server酱 `sendkey` 不得写入仓库、聊天记录或文档。

GitHub Secrets 名称：

- `SERVER_CHAN_SENDKEY`

用途：

- `.github/workflows/weekly-ops.yml` 在通知步骤读取该 secret。
- `scripts/notify/server-chan.ts` 只从环境变量读取，不记录密钥。

手动测试：

- 进入 GitHub Actions。
- 选择 `AI Outpost weekly ops`。
- 点击 `Run workflow`。
- 如果配置正确，微信应收到一条周更检查结果通知。

### GitHub Actions 定时注意事项

- GitHub Actions 定时任务运行在默认分支。
- 默认使用 UTC cron。北京时间 2026-06-20 17:00 对应 UTC 09:00。
- GitHub 官方说明定时任务在高峰期可能延迟，整点附近尤其容易拥堵。
- 为降低延迟风险，当前 workflow 使用 17:05，即 UTC `5 9 * * 6`。如果用户坚持 17:00，则改为 UTC `0 9 * * 6`，但需要接受可能延迟。

## 官网一键发布最小路径

第一阶段官网发布仍保留人工确认。最小路径可以定义为：

1. GitHub Actions 定时生成草稿和校验报告。
2. GitHub Actions 通过微信推送服务通知用户。
3. 用户确认发布。
4. 用户手动触发官网发布 workflow，或在后续版本通过确认链接触发发布 workflow。
5. 发布 workflow 将目标 issue 从 `approved` 切换为 `published`，填写 `publishedAt`。
6. 发布 workflow 运行发布前检查。
7. GitHub Pages workflow 构建并部署。
8. AI 或用户检查公开链接。

这个路径仍需要用户确认，不允许自动绕过。

## 公众号发布待讨论

需要单独确认：

- 是否已有微信公众号。
- 账号类型：订阅号、服务号或个人创作者能力，待确认。
- 是否能使用草稿箱 API，待确认。
- 是否需要封面图、摘要、作者、原文链接。
- 是否接受“自动生成公众号 Markdown，人工复制到后台”的第一阶段方案。

建议第一阶段：

- 先做公众号 Markdown 草稿。
- 人工复制到公众号后台。
- 等流程稳定后，再研究草稿箱 API 或其他自动发布方式。

## 小红书发布待讨论

需要单独确认：

- 发布内容是“AI 周报”还是“作品集 / 案例合集”。
- 是否需要图文卡片图片，而不只是文字。
- 小红书合集、专栏或分类能力待确认。
- 是否用同一账号发布多种内容，还是拆账号。

建议第一阶段：

- 只生成小红书图文卡片文案。
- 暂不自动生成图片和发布。
- 等用户确认内容形式后再做图片模板。

## X / Twitter 发布待讨论

需要单独确认：

- 是否注册账号。
- 是否接受英文短帖。
- 是否需要 API 自动发布，相关权限和费用待确认。
- 是否只做手动复制发布。

建议第一阶段：

- 只生成短帖草稿。
- 不接 API。
