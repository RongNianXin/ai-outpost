# 第 002 期稳定周更任务包

## 目标

第 002 期不是单次手工写稿任务，而是 V1.5 稳定周更自动化的第一次流程演练。目标是验证 AI Outpost 能否在尽量少人工介入的情况下，稳定完成候选收集、筛选、核验、写作、预览和确认后上线。

本任务包当前是运行说明，不代表所有步骤已经脚本化。执行时可以由 AI 按本文逐步完成；后续再把高频步骤固化为脚本。

## 成功标准

- 生成一份可发布的第 002 期结构化 JSON，或明确给出本周短版/跳过原因。
- 全部硬事实能追溯到官方来源。
- 专家博客、社区热帖或社交媒体只用于最多 1 条“前沿概念观察”，不得作为硬事实来源。
- 用户只需要阅读中文确认摘要、预览链接和风险提示。
- 未获得用户确认前，不得切换为 `published`，不得触发公开发布。
- 如内容不足、核验冲突、预算超限或构建失败，保留线上上一期。

## 非目标

- 不做微信公众号、小红书、X/Twitter 自动发布。
- 不要求用户注册或登录外部平台。
- 不引入数据库、CMS、后台服务或长期运行服务器。
- 不为了第 002 期新增复杂页面功能。
- 不把未经核验的专家观点写成行业事实。

## 运行状态

每次周更先检查运行状态。第一版可以手动创建文件，后续再脚本化。

建议文件：`ops/weekly-run-state.json`

```json
{
  "mode": "normal",
  "weekId": "2026-WXX",
  "issueId": "issue-002",
  "startedAt": null,
  "lastStep": "not_started",
  "requiresUserConfirmation": true,
  "failureReason": null
}
```

字段规则：

- `mode` 可选：`normal`、`paused`、`draft_only`、`emergency_stop`。
- `paused`：停止本周流程，不生成新期。
- `draft_only`：只生成草稿、审核摘要和分享包，不进入公开发布。
- `emergency_stop`：任何发布相关动作都必须退出。
- `requiresUserConfirmation` 默认为 `true`，第 002 期不得关闭。

## 运行日志

建议文件：`ops/runs/<weekId>.json`

日志至少记录：

- 周期窗口：开始日期、结束日期、运行时间。
- 候选总数、淘汰数、保留数。
- 每条候选的来源、发布日期、来源类型、保留/淘汰原因。
- AI 质检结果：来源真实性、事实映射、反向质疑、中文编辑、总质检。
- 自动检查结果：`content:validate`、`content:check:links`、`content:export:wechat`、`typecheck`、`lint`、`test`、`build`。
- 最终状态：等待确认、已发布、短版、跳过、失败。
- 失败原因和下一步建议。

## 周期窗口

- 默认使用上一完整自然周，按 Asia/Shanghai 计算。
- 如果遇到第一轮演练、节假日或重大事件，可由用户确认后调整窗口。
- 不猜测日期；所有候选必须记录原始发布日期或明确说明日期不可确认。

## 候选来源

### 官方硬事实来源

优先检查：

- OpenAI、Anthropic、Google AI、GitHub、Microsoft、Cursor 等官方博客、官方文档、更新日志和 GitHub Releases。
- 与 AI 应用开发、Agent、模型、开发工具、RAG、多模态、部署和安全直接相关的官方更新。

保留条件：

- 来源身份明确。
- 有可访问的原始链接。
- 发布日期清楚。
- 变化对 AI 应用开发者有实际影响。
- 能定位到具体证据位置。

### 前沿概念观察来源

允许检查：

- AI 大厂负责人、核心工程师、知名开源维护者或长期输出的 AI 工程专家。
- 专家博客、社区热帖或被多位业内人士讨论的概念。

限制：

- 每期最多 1 条。
- 必须标注“官方背书弱、概念未稳定”。
- 只能写观察价值，不能写成确定趋势。

## 候选筛选规则

候选上限：20 条。

优先保留：

- 对 AI 应用开发者工作流有直接影响。
- 涉及模型能力、模型退役、工具权限、Agent 工作流、API 变化、部署和安全边界。
- 官方证据清楚，限制条件明确。

直接淘汰：

- 只有媒体转载，没有官方来源。
- 日期不明。
- 来源身份不清。
- 只是营销表述，没有可验证事实。
- 与目标读者关系弱。
- 需要用户继续阅读英文才能判断真伪。

排序维度：

- 相关性。
- 变化程度。
- 开发者影响。
- 证据清晰度。
- 风险可控性。

## 内容结构

第 002 期默认结构：

- 正式情报卡最多 6 张。
- 重点信号最多 3 条。
- 同一厂商原则上不超过 2 条。
- 前沿概念观察最多 1 条。
- 如果只有 1 至 3 条高质量内容，可发布短版。
- 如果没有足够可靠内容，跳过本周，并保留运行记录。

每张情报卡必须包含：

- 标题。
- 发布方。
- 发生日期。
- 一句话事实摘要。
- 为什么重要。
- 对开发者的影响。
- 阅读建议。
- 风险等级。
- 来源引用。
- 事实支撑和限制条件。

## AI 质检角色

第 002 期继续使用六角色核验：

1. 候选发现 Agent：只记录发生了什么，不生成影响结论。
2. 来源真实性 Agent：确认域名、组织、页面、发布日期和最终 URL。
3. 事实与证据映射 Agent：把中文事实句映射到官方证据位置。
4. 反向质疑 Agent：主动寻找夸张、遗漏、混淆和冲突。
5. 中文编辑 Agent：只用已通过事实写成新手可读中文。
6. 总质检 Agent：决定适合发布、需要修改、降级或删除。

任一硬事实出现 `REJECT` 或 `UNSUPPORTED`，直接删除或降级，不进入发布稿。

## 预算控制

第一版预算先用规则控制，不接入付费统计系统。

- 候选最多 20 条。
- 正式内容最多 6 条。
- 单条候选最多允许 2 轮修正。
- 同一失败检查最多重试 2 次。
- 自动链接检查出现网络波动时记录警告，不无限重跑。
- 如果 AI 质检冲突超过 3 条，停止写稿，先生成风险报告。

## 执行步骤

### 1. 启动检查

输入：

- `task_plan.md`
- `findings.md`
- `progress.md`
- `docs/CONTENT-OPS.md`
- `docs/FACT-CHECK-PROTOCOL.md`
- `content/sources.json`

动作：

- 确认第 001 期已发布。
- 确认本轮目标是第 002 期。
- 检查运行状态是否允许继续。
- 确认本轮周期窗口。

输出：

- 本轮 `weekId`。
- 本轮候选收集范围。
- 是否继续、仅草稿、暂停或停止。

### 2. 候选收集

动作：

- 检查官方白名单来源。
- 记录候选标题、URL、发布者、发布日期、来源类型和一句话事实。
- 可额外记录 0 至 3 条前沿概念观察候选，最终最多保留 1 条。

输出：

- 候选清单。
- 初步淘汰清单。

### 3. 筛选和排序

动作：

- 删除重复、日期不明、无官方来源、弱相关候选。
- 按相关性、影响和证据清晰度排序。
- 选出最多 6 条正式候选。

输出：

- 正式候选。
- 备选候选。
- 淘汰原因。

### 4. 事实核验

动作：

- 对每条正式候选运行来源真实性、事实映射和反向质疑。
- 高风险事实必须额外保守处理。
- 专家观点必须明确降级为观察。

输出：

- 每条候选的核验结论。
- 删除、降级或保留建议。

### 5. 中文编辑和 JSON 草稿

动作：

- 只用已通过事实写中文。
- 生成 `content/issues/issue-002.json` 草稿。
- 状态保持 `draft`。
- 不填写 `publishedAt`。

输出：

- 第 002 期草稿 JSON。
- 自动验证摘要草稿。

### 6. 自动检查

必须运行：

```powershell
pnpm.cmd content:validate
pnpm.cmd content:check:links
pnpm.cmd content:export:wechat
pnpm.cmd typecheck
pnpm.cmd lint
pnpm.cmd test
pnpm.cmd build
```

处理：

- 任一结构、类型、测试或构建失败，停止发布。
- 链接明确 404 或 5xx，删除对应内容或停止本期。
- 403、405、超时或网络异常记录为警告，按保守规则处理。

### 7. 预览和确认摘要

输出给用户：

- 第 002 期中文标题。
- 本期 3 条以内核心变化。
- 正式情报卡数量。
- 最高风险点。
- 被删除的候选和原因。
- 链接检查警告。
- 本地或公开预览方式。
- 建议操作：确认发布、仅草稿、暂停、跳过。

用户只做判断：

- 标题是否清楚。
- 内容是否有用。
- 是否确认上线。

### 8. 确认后发布

只有用户明确确认后才执行：

- 填写 `previewApprovedAt`。
- 将状态改为 `approved`。
- 准备公开发布时填写 `publishedAt`。
- 将状态改为 `published`。
- 运行发布前检查。
- 触发 GitHub Pages 发布流程。

未确认时：

- 保持 `draft` 或 `approved`。
- 不公开发布。

### 9. 发布后记录

更新：

- `progress.md`
- 必要时更新 `findings.md`
- 必要时更新 `task_plan.md`
- 运行日志文件

记录：

- 是否发布。
- 发布时间。
- 公开链接。
- 检查结果。
- 错误或警告。
- 下期改进项。

## 短版和跳过规则

短版适用：

- 只有 1 至 3 条高质量官方事实。
- 内容虽少，但对 AI 应用开发者有明确价值。

跳过适用：

- 没有足够可靠官方来源。
- 候选都缺少日期或证据。
- AI 质检冲突无法解决。
- 构建或链接检查失败且无法安全修复。

跳过时也要输出：

- 本周检查了哪些来源。
- 为什么不发布。
- 是否有值得下周继续观察的候选。

## 分享包

第 002 期可以生成分享包，但不是发布必须项。

可选输出：

- 官网分享标题。
- 朋友圈/微信群短文。
- 公众号 Markdown 草稿。
- 小红书图文卡片文案或图片素材建议。
- X/Twitter 短帖草稿。

限制：

- 分享包不能新增事实。
- 小红书和 X/Twitter 不要求账号，不自动发布。
- 平台合规扫描能力待确认，前期只做明显高风险词和夸张表述提示。

## 第 002 期完成定义

满足以下任一结果即可视为完成：

- 完整发布：第 002 期通过检查，经用户确认后发布到官网。
- 短版发布：高质量内容不足 6 条，但通过检查，经用户确认后发布短版。
- 合理跳过：没有可靠内容或存在高风险阻塞，生成跳过报告并记录到进度。

未完成状态：

- 只有候选清单，没有核验。
- 有草稿，但未通过检查。
- 有检查结果，但未生成中文确认摘要。
- 未经用户确认却切换为 `published`。

## 后续脚本化候选

后续可以逐步新增命令：

- `content:weekly:state`
- `content:weekly:collect`
- `content:weekly:review`
- `content:weekly:generate`
- `content:weekly:verify`
- `content:weekly:summary`
- `content:weekly:publish`

脚本化顺序应先做状态读取和运行日志，再做候选收集和自动生成，不要一开始就做平台发布。
